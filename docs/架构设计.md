# 选品 Agent 架构设计文档

> 对话式选品 Agent 的技术架构。每个设计决策标注理由和被否方案（ADR），已知限制诚实列出。
> 阅读配套：[调优指南](./调优指南.md)（可调资产与调优平台规格）、[README](../README.md)（快速开始）。

---

## 1. 系统概述

### 1.1 定位

餐饮供应链 B2B 场景的选品助手：用户用自然语言提出选品需求（竞对 × 城市 × 品类），Agent 识别该口径下竞对平台的高销品，产出结构化推荐清单（含可追溯的推荐理由）。

### 1.2 任务定义

- **输入**：自然语言对话（多轮，支持追问与解释类问题）
- **输出**：① 流式自然语言总结；② 结构化推荐清单（商品、类目、命中策略、关键数据、推荐理由）
- **口径**（Core Spec）= 竞对 × 城市 × 品类，是整个系统的核心抽象

### 1.3 关键约束

| 约束 | 说明 | 架构影响 |
|---|---|---|
| 竞对数据异构 | 6 个竞对分三种数据覆盖档位：有销量 / 仅库存 / 均无 | 三条策略路径 + 运行时动态路由（§4） |
| 商品标题是脏数据 | 营销词/规格/emoji 混杂，如「【门店专供】精品五花肉片500g✨烧烤专用」 | 类目对齐是唯一必须交给 LLM 的语义环节 |
| 数值可信是底线 | 推荐理由中的数字必须可追溯 | 数值计算与生成分离（ADR-1） |
| 部署环境简单 | 本地 / Vercel Serverless 双跑 | 无数据库、无服务端会话状态（ADR-5/6） |

## 2. 总体架构

```
┌─ 用户界面层（src/app/page.tsx）─────────────────────────┐
│  对话流渲染：消息 / 工具气泡(可展开) / 推荐卡片(数字高亮)  │
├─ API 层（src/app/api/*）────────────────────────────────┤
│  /api/chat  SSE 流式对话    /api/health  模式探测        │
│  /api/meta   类目名映射                                   │
├─ 编排层（src/lib/agent/chat-runner.ts）─────────────────┤
│  多轮 ReAct 循环：口径解析(模型驱动) → 工具调用 → 流式回复 │
│  历史上下文重建 / 澄清与执行的分岔 / 步数护栏             │
├─ 工具层（src/lib/agent/tools/）─────────────────────────┤
│  T1 数据覆盖探测   T2 销量榜单    T3 库存推算             │
│  T4 多因子评分     T5 商品语义对齐(LLM)  T6 推荐理由生成  │
│  registry：function calling 定义组装 + resolveSpec 口径解析│
├─ 数据层（src/lib/storage/ + data/*.json）───────────────┤
│  竞对 / 类目 / 类目知识数据集 / 商品(含真值) / Prompt版本  │
│  只读、静态打包、globalThis 单例                          │
├─ 模型层（src/lib/llm/client.ts）────────────────────────┤
│  DeepSeek（OpenAI 兼容）· temperature=0 · 流式 + 重试    │
└─────────────────────────────────────────────────────────┘
```

各层只依赖相邻下层；数据层被工具层和编排层共同读取。

## 3. 核心执行流程

### 3.1 一轮完整对话的时序

```
用户："竞对D在杭州的蔬菜蛋品有什么高销品？"
  │
  ▼
[POST /api/chat] 服务端重建消息序列：
  system = pv.systemPrompt + 对话模式指令(动态生成竞对/品类清单)
  + 历史(带推荐清单的轮次注入结构化数据)
  │
  ▼
ReAct 循环（上限 8 轮模型调用）
  ├─ 模型输出 tool_calls → 解析参数 → 执行工具 → 结果回填 → 继续循环
  │    T1 探测: {competitorId:"comp-d", city:"杭州", parentId:"cat-sc"}
  │        → resolveSpec 落地口径 → coverage: "sales"
  │    T2 榜单: top20% 且 ≥200 件 → 8 个候选(带销量)
  │    T5 对齐: 注入类目枚举+边界规则+few-shot → 每品返回类目+置信度
  │    T6 理由: 模板化生成，数字来自工具返回值占位符
  │    （工具全部执行完 → assembleOutput 组装推荐清单 → 推送 run_complete）
  └─ 模型输出纯文本 → 结束循环
  │
  ▼
SSE 事件流推给前端（全过程）：
  token(逐段文本) → tool_start/tool_end(每个工具) →
  run_complete(推荐清单) → done(最终总结)
```

### 3.2 澄清与执行的分岔（无前置意图识别）

模型对每条用户消息二选一，**由模型自己决定，代码不干预**：

- **口径完整** → 直接调 T1（口径表达在工具参数里，见 ADR-2）
- **口径缺项** → 输出纯文本澄清问题（如「想看哪个城市的？」），本轮无工具调用
- **追问** → 延续上文口径只替换变化项（「那上海呢」→ 只换城市重新执行）
- **解释类问题** → 基于历史中的工具数据回答，必要时再调工具

### 3.3 追问的上下文机制（ADR-4）

客户端持有完整对话历史；带推荐清单的历史轮次在服务端重建时附加结构化数据：

```
assistant: "已完成竞对A北京半熟调理的分析…"
           [本轮推荐清单数据]
           [{"商品":"奥尔良腌鸡腿肉…","类目":"bs-yw","策略":"S1-销量榜单","销量":2093},…]
```

模型因此能回答「为什么推荐这个」并正确处理「换成调味酱料」这类部分替换。

## 4. 工具层详细设计

每个工具标注「数值/语义」属性——这是人机分工原则的落地。

### T1 数据覆盖探测（数值）

探测口径数据质量并**落地口径**：对话模式下 `resolveSpec` 优先取模型传入的 competitorId/city/parentId（自然语言解析结果），非法组合报错引导模型自纠（ADR-2）；参数缺失回退当前口径。返回 `{coverage, dataVolume, lastUpdate, spec}`。

### T2 销量榜单（数值，策略一）

类目内销量 top20% 且 ≥200 件（30 天窗口）。`topPct`/`minSales` 由模型传入——参数选择本身是 agent 的决策点。默认参数与金标口径一致。适用于 coverage=sales 的竞对（A/D）。

### T3 库存推算（数值，策略二）

3 天窗口差值算法：周期内两两做差 → 剔除负差值（补货）→ 取最大正差值 → 各周期累加（保守下限），9 天快照推算 30 天。适用于 coverage=inventory（B/E）。对错误策略调用返回引导性错误（模型可据此换工具）。

### T4 多因子评分（数值，策略三）

四因子加权：近 7 天促销 / 近 30 天持续在售 / 近 180 天长期有效在售 / 渠道标签。权重是可调资产（PromptVersion 携带）。适用于 coverage=none（C/F）。因子均为代理信号，准确率天然低于策略一——宁可漏检不误推。

### T5 商品语义对齐（语义，唯一 LLM 语义入口）

竞对脏标题 → 标准类目（封闭枚举）。知识注入按品类动态裁剪：该品类的叶子类目枚举 + 类目知识数据集（边界规则 + few-shot 样例）。归属不确定输出 `PENDING`（待人工复核），禁止猜测。输出含置信度。

### T6 推荐理由生成（语义，模板化）

三段式模板：命中策略 + 关键数据 + 卖家价值点。**数字从工具返回值占位符填充，模型只组织语言**（ADR-3 的落地）。`keyNumbers` 随输出透出，供前端高亮和数值一致性检测。

### 输出组装（assembleOutput）

推荐清单由**工具链结果组装**而非解析模型文本：T6 的商品集 × T5 的类目 × 策略工具的 metric/score。模型的最终文本只是总结，不是数据源。

## 5. 编排层设计

| 机制 | 设计 | 理由 |
|---|---|---|
| ReAct 循环 | 上限 8 轮模型调用 | 探测→路由→执行→对齐→理由→总结的合理范围，防死循环 |
| 流式协议 | SSE，六种事件（token/tool_start/tool_end/run_complete/done/error） | 单向推送够用；工具气泡与文本逐段渲染（ADR-7） |
| 工具调用流式组装 | chatCompletionStream 按 index 增量拼接 tool_calls 分片 | function calling 与 token 流式兼得 |
| 请求幂等 | 服务端零会话状态，每次全量重放历史 | 无状态可水平扩展，Vercel 免持久化（ADR-5） |
| 重试 | LLM 调用 3 次指数退避 | 网络抖动兜底，不改变语义（temperature=0） |

## 6. 数据层设计

### 6.1 数据资产（data/*.json）

| 文件 | 内容 | 规模 |
|---|---|---|
| competitors.json | 6 竞对（三种覆盖档位各两个）× 城市覆盖 | 6 |
| categories.json | 12 品类 × 42 叶子类目（含易混淆组标记） | 54 |
| category-knowledge.json | 类目知识数据集（kv-v0/v1/v2 三个版本） | 4 类目有规则 |
| products.json | 商品（脏标题 + 真值字段） | 3924 |
| prompts.json | Prompt 版本（systemPrompt + 六工具描述 + 参数） | 1（v1.1） |

数据由 `scripts/generate-data.ts` 固定种子生成，可重复执行（ADR-8）。

### 6.2 真值字段设计（为评测预留的钩子）

| 字段 | 含义 | 用途 |
|---|---|---|
| `trueCategoryId` | 真值叶子类目 | 类目对齐准确率的分母 |
| `trueSales30d` | 底层真实销量（对销量竞对同时是观测值） | 金标计算 |
| `goldCities` | 该商品在哪些城市属策略一金标（top20% 且 ≥200） | 选品准召率基准 |
| `isBoundaryCase` | 类目边界难点商品（60 个，标题关键词交叉） | E1 错误的归因切片 |

平台即使不建，这些字段也支持「对话后手工核对」的调优验证。

### 6.3 存储

静态 import 打包（非运行时读文件）：本地与 Vercel 行为一致，冷启动无 IO；globalThis 单例避免开发模式热重载重复实例化。代价是数据不可运行时写（调优平台需要持久化时另加运行时层，见调优指南 §5）。

## 7. 模型层设计

| 项 | 决策 | 理由 |
|---|---|---|
| 模型 | DeepSeek（OpenAI 兼容协议） | 成本低、function calling 稳定；协议兼容意味着可平替 |
| temperature | 0 | 同输入同输出，可复现是调优验证的前提 |
| 上下文 | system(约 1K token) + 历史 + 工具定义 | 多轮对话控制在 8K 内 |
| 单轮成本 | 约一次完整选品 3-6K token | 单次对话约几分钱 |

## 8. 设计决策记录（ADR）

| # | 决策 | 理由 | 被否方案 |
|---|------|------|---------|
| ADR-1 | 数值计算全部在确定性工具，LLM 只做语义（对齐/路由/理由组织） | 幻觉的破坏面锁死在可校验的语义层 | 全链路交给 LLM（数值不可信） |
| ADR-2 | 口径解析放在工具参数层（resolveSpec），不做前置意图识别模块 | 少一次 LLM 调用；解析错误由工具校验兜底并引导自纠；口径表达与执行天然耦合 | 前置 NLU 先行解析口径（多一跳、错误不可自纠） |
| ADR-3 | 推荐清单由工具链结果组装，不解析模型最终文本 | 结构化数据零幻觉；模型文本仅作总结 | 解析模型输出的 JSON（格式不稳、数字可能被改写） |
| ADR-4 | 会话状态在客户端，服务端每次全量重放（含结构化清单注入） | 服务端无状态；追问有据可答；刷新即恢复 | 服务端 session 存储（需持久化、扩容复杂） |
| ADR-5 | 无数据库，数据静态打包 | 规模小、部署零依赖、本地线上一致 | SQLite/外部 DB（对当前规模是负资产） |
| ADR-6 | 类目映射用封闭枚举，不用 RAG | 42 个叶子类目直接枚举即可，向量检索无增益 | embedding 检索（复杂度换不来收益） |
| ADR-7 | SSE 而非 WebSocket | 单向事件流，HTTP 语义简单，Vercel 原生支持 | WebSocket（双向能力用不上，运维成本高） |
| ADR-8 | 数据由脚本固定种子生成 | 可重复、可版本化、真值可控 | 手工维护数据（不可控且无法回溯） |
| ADR-9 | 澄清行为由系统提示约束，由模型自主决定 | 澄清时机是语义判断，硬编码规则覆盖不了表达多样性 | 代码层强制先解析后确认（回到 ADR-2 被否方案） |

## 9. 成本与性能

| 维度 | 量级 | 说明 |
|---|---|---|
| 单轮对话延迟 | 首个 token 约 1-2s，完整选品 20-60s | 4 次工具调用 + 2-3 次模型生成，流式感知良好 |
| 单轮 token | 3-6K | system ~1K + 工具定义 ~1K + 工具结果回填 + 生成 |
| 单轮成本 | 约几分钱（DeepSeek） | 日常演示可忽略 |
| Vercel 限制 | /api/chat maxDuration=120s | Serverless 超时上限内 |

## 10. 已知限制与开放问题

| # | 限制 | 现状 | 影响 |
|---|------|------|------|
| L1 | **无运行记录持久化**：对话即焚，刷新后历史在客户端但服务端无 case 资产 | 调优平台需求（PR1 解决） | 无法批量评审与回归 |
| L2 | **无自动回归**：改提示词后只能手工 A/B（固定问题集） | 调优指南 §4 的手工流程 | 迭代验证靠人肉 |
| L3 | **类目知识只覆盖肉类边界组**：腐竹/干鲜菌菇/淀粉粉条等混淆组无规则 | 调优指南 §3 的练习题 | T5 在这些组会真实出错 |
| L4 | **T5 置信度依赖模型自报**：无外部校准，可能过度自信 | PENDING 兜底 | 低置信漏标 |
| L5 | **追问依赖历史重放的完整性**：超长对话上下文膨胀（每次重放全部清单数据） | 8 轮内无压力 | 多轮长对话需裁剪策略 |
| L6 | **无并发/限流保护**：单用户演示场景 | 公开部署可被刷 token | 需要时加简单鉴权或速率限制 |
| L7 | **开放问题**：趋势选品（时间窗对比）、城市对照（多口径并行）两类任务未实现 | 当前只有口径选品（Type A） | 属能力扩展方向：加任务类型不加工具 |
