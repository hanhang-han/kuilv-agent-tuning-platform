# 选品 Agent 调优指南

> 给两类人：①想把这个 agent 调得更好的人；②要在这个 agent 之上构建「调优平台」的开发者。
> 所有可调资产的位置、修改方法、验证流程、平台需求规格都在这里。

---

## 一、调优地图：六个可调层

| 调优层 | 调什么 | 源码位置（改这里） | 运行时文件 | 影响什么 |
|---|---|---|---|---|
| ① 工具描述 | T1-T6 的功能说明与**边界条件** | `scripts/generate-data.ts` → `T5_DESC_GOOD` / `baseToolDescs` | `data/prompts.json` → `toolDescriptions` | 模型对工具的理解与调用质量；T5 描述直接决定类目对齐（E1） |
| ② 类目知识数据集 | 每个类目的边界规则 + few-shot 样例 | `scripts/generate-data.ts` → `KNOWLEDGE_VERSIONS` | `data/category-knowledge.json` | T5 语义对齐的知识来源（E1） |
| ③ 系统提示词 | 角色设定、任务流程、工具使用规则 | `scripts/generate-data.ts` → `SYSTEM_PROMPT_V1` | `data/prompts.json` → `systemPrompt` | 整体行为纪律（数值不编造、宁缺毋滥） |
| ④ 对话指令 | 澄清策略、追问处理、总结表达 | `src/lib/agent/chat-runner.ts` → `buildChatInstruction()` | （编译进代码） | 对话体验：何时追问、怎么总结 |
| ⑤ 策略参数 | T4 四因子权重、T2 销量门槛 | 权重：`generate-data.ts` → `W_CAL`；门槛：`src/lib/agent/tools/t2-sales.ts` | `data/prompts.json` → `t4Weights` | 选品口径的松紧（误推 vs 漏检） |
| ⑥ 理由模板 | T6 三段式结构与话术 | `src/lib/agent/tools/t6-reason.ts` → `templateReason()` | （编译进代码） | 推荐理由的可信度与说服力（E3） |

**修改后生效三步**：`npm run generate`（①②③⑤需要）→ 重启 `npm run dev` → 对话验证。

**设计原则**（改任何东西前先记住）：①②③④是语义层，随便调；⑤的数值计算永远在确定性代码里，模型不碰数字。这条线是幻觉的防线，不要跨。

## 二、各层详解与修改示例

### 2.1 工具描述（见效最直接的一层）

工具描述是模型理解工具的**唯一依据**——相当于 agent 时代的 API 文档 + 产品文案。写得含糊，模型就会误调用、误传参、误判边界。

**T5 的描述是重中之重**，因为类目对齐是全链路唯一的 LLM 语义入口。当前描述里写死了肉类边界组的四条规则。一个经典的改前后对比：

```
改前（含糊版）：
  「将竞对商品标题映射到快驴标准类目，输出对应类目 ID。」

改后（边界版，即当前版本）：
  「将竞对商品标题映射到快驴标准类目。关键边界规则：腌制/调味/酱制处理过的
   肉制品（未穿串）归『腌制烤肉类』；穿串/穿签预处理（无论是否腌制）归
   『烧烤串类』；仅含烹饪建议词（如"烧烤用""火锅用"）的未加工鲜肉归
   『鲜分割肉类』；冷冻的未加工肉归『冷冻肉类』。归属不确定时输出
   『待人工复核』，禁止猜测。」
```

改前，「烧烤用鲜羊肉块」（未加工鲜肉）会被「烧烤」关键词带偏到烤肉类；「现穿羔羊肉串 腌制入味」会被「腌制」带偏到腌制类。规则的本质是**写清边界条件，而不是罗列功能**——和写 PRD 定义需求边界是同一件事。

### 2.2 类目知识数据集

与工具描述的分工：**工具描述管「怎么用工具」，知识数据集管「注入什么领域知识」**。T5 每次调用时，会把当前品类下的叶子类目枚举 + 对应的边界规则 + few-shot 样例拼进提示词（见 `src/lib/agent/tools/t5-align.ts`）。

当前结构（kv-v2，4 个类目有规则，每类 2 个样例）：

```json
{
  "categoryId": "bs-cc",
  "boundaryRules": "穿串、穿签预处理的商品归本类，无论是否腌制（穿串优先于腌制判断）。",
  "fewShots": [
    { "title": "现穿羔羊肉串 腌制入味", "categoryId": "bs-cc" },
    { "title": "生穿鸡肉串 未腌制", "categoryId": "bs-cc" }
  ]
}
```

调优动作：给新的混淆组补规则（见第三节「练习题」）、给判错过的标题补 few-shot 样例。few-shot 的来源应该是真实判错案例的回流——这是知识数据集能持续变好的机制。

### 2.3 系统提示词

当前版本定了四条纪律：先探测再路由（T1）、数值结论必须来自工具返回、不确定输出待人工复核、宁缺毋滥。调优时注意：**加规则容易，删规则难**——规则越多模型遵循越差，每加一条都要想清楚它防的是什么错误。

### 2.4 对话指令

对话模式特有的层：缺口径先澄清还是给默认值、追问只替换变化项、总结时每个商品一句话。这一层调的是「对话体验」，改完不需要 `npm run generate`，重启即可。

### 2.5 策略参数

- **T4 权重**（促销/持续在售/长期在售/渠道标签，和必须为 1）：调的是「没有销量数据时，什么信号更可信」。判断标准：用有销量口径的金标回测——权重改完去问无数据竞对（C/F），看推荐与真值销量的重合度
- **T2 门槛**（top20% 且 ≥200 件）：调的是选品松紧。门槛调高 → 推荐更少更稳（宁缺毋滥），调低 → 召回上来但误推风险增加。这是业务判断，不是技术参数

### 2.6 理由模板

当前是三段式：命中策略 + 关键数据 + 卖家价值点，数字全部由工具返回值占位符填充。可调方向：话术风格（专业/口语）、数据呈现（件数/排名/环比）、价值点角度（毛利/周转/引流）。

## 三、已知类目混淆点（调优练习题）

**已覆盖**：肉类边界组（腌制烤肉类 / 烧烤串类 / 鲜分割肉类 / 冷冻肉类）——60 个边界难点商品全部埋在这个组，规则已写进工具描述和知识数据集。

**未覆盖**（当前无规则，模型大概率会错，是最好的调优练习素材）：

| 混淆点 | 涉及类目 | 建议规则写法 |
|---|---|---|
| 腐竹、豆皮 | 蔬菜蛋品/豆制品类 vs 农副干货 | 「腐竹、豆皮等干货形态的豆制品仍归豆制品类，不因干燥形态归入农副干货」 |
| 鲜香菇 vs 干香菇 | 蔬菜蛋品/食用菌类 vs 农副干货/菌菇干货类 | 「鲜菌归食用菌类；干香菇、干木耳等干制菌菇归菌菇干货类。标题含『干』『干货』字样优先判干货」 |
| 茶树菇 vs 茶树菇干 | 同上 | 同上 |
| 土豆淀粉 vs 土豆粉条 | 米面粮油/面粉类 vs 农副干货/粉丝粉条类 | 「淀粉归面粉类；成型粉条/粉丝归粉丝粉条类」 |
| 柠檬茶（饮料）vs 茶叶 | 酒水饮料/饮料类 vs 茶饮咖啡/茶叶类 | 「即饮/冲饮型柠檬茶归饮料类；原料茶叶归茶叶类」 |
| 蛋挞皮、泡芙壳 | 休闲零食/糕点类 vs 烘焙原料 | 「蛋挞皮、泡芙壳等烘焙半成品归烘焙原料；成品糕点归糕点类」 |

**练习方法**：先问相关口径（如「竞对A北京的蔬菜蛋品」「竞对D杭州的茶饮咖啡」）观察判错 → 在知识数据集加规则 → 重新生成 → 同一问题再问，对比判对情况。

## 四、验证方法：无平台的 A/B 流程

调优最怕「改好一处、改坏三处」。没有平台时用固定问题集做手工回归：

**固定问题集**（覆盖三条策略路径 + 边界商品密集口径）：

```
1. 竞对A在北京的半熟调理有什么高销品？      （策略一 + 肉类边界组）
2. 竞对D在杭州的蔬菜蛋品有什么高销品？      （策略一 + 豆制品/菌菇混淆组）
3. 竞对B在上海的生鲜肉类有什么值得引入的？   （策略二库存推算）
4. 竞对E在广州的农副干货推荐一下            （策略二 + 干货混淆组）
5. 竞对C在成都的调味酱料有什么选品机会？     （策略三多因子）
6. 竞对F在重庆的茶饮咖啡呢？                （策略三 + 茶叶混淆组）
7. 那武汉呢？                              （追问：口径延续）
8. 为什么推荐第一个商品？                    （解释：数据可追溯）
```

**对比要点**（每次调优前后各跑一遍）：
- 推荐数量是否合理（6-9 条为正常区间）
- 边界商品的类目判对没有（展开 T5 工具调用看输出）
- 理由中的数字与工具返回一致吗（数字高亮，逐个核对）
- 有没有引入新错误（原来判对的现在错了？）

## 五、构建调优平台：需求规格（vibe coding 直接可用）

如果评 case 和手工 A/B 成为日常负担，就该把调优流程产品化了——这正是调优平台的由来。以下规格可以直接作为 vibe coding 的需求输入。

### 5.1 平台解决什么问题

1. **评 case 苦**：agent 每次运行的决策链路和输出散落在对话里，没有结构化记录，无法批量评审
2. **口径在脑子里**：什么算对（尤其是类目判对）没有标准化，换个人评就不一致
3. **改动无法回归**：改了提示词/知识，只能手工问几个问题，发现不了「改好一处改坏三处」

### 5.2 建议模块（四件套）

| 模块 | 功能 | 对标 |
|---|---|---|
| Case 池 | agent 运行记录全量列表（口径、决策链路、输出、评审状态），按竞对/品类/状态筛选 | LangSmith trace 列表 |
| 评审工作台 | 单 case 详情：决策链路时间线（每个工具调用的输入输出）→ 输出清单 → 通过/打回 + 错误类型标注 | LangSmith 标注队列 |
| 归因看板 | 错误类型分布、趋势、按竞对/品类切片 | LangSmith 看板 |
| Prompt 实验室 | 提示词/工具描述/知识数据集/参数的版本管理 → 修改 → 固定口径集回放 → 版本对比 | Promptfoo 回归测试 |

### 5.3 数据钩子（agent 侧已就绪的接口）

**Case 记录来源**：`runChatConversation()`（`src/lib/agent/chat-runner.ts`）的事件流已包含构建 case 的全部信息——每个 `tool_end` 事件是一条工具调用记录（输入/输出/耗时），`run_complete` 事件带结构化推荐清单。平台只需包装这个函数，把事件流持久化即可。

**评测真值**（自动计算指标的关键，都在 `data/products.json`）：

| 字段 | 含义 | 支持的指标 |
|---|---|---|
| `trueCategoryId` | 商品的真值叶子类目 | 类目对齐准确率（E1 检测） |
| `goldCities` | 该商品在哪些城市属策略一金标（真值销量 top20% 且 ≥200） | 选品准召率（vs 金标） |
| `isBoundaryCase` | 类目边界难点商品 | E1 归因切片（边界商品错误率） |
| `trueSales30d` | 底层真实销量 | 无数据口径的推荐质量回测 |

**理由数值一致性（E3 检测）**：推荐清单每条带 `keyNumbers`（工具返回的真值数字）和 `reason`（理由文本），从理由中提取数字与 keyNumbers 比对即可自动检测幻觉。

### 5.4 自动指标定义

```
格式合规率   = Validator 通过的 case 数 / 总 case 数
类目对齐准确率 = 输出条目 categoryId == trueCategoryId 的比例（品级）
理由数值一致率 = 理由中的数字与 keyNumbers 一致的比例（品级）
选品准召率   = 输出清单 vs goldCities 金标（仅销量口径竞对 A/D 有意义）
```

注意**双层口径**：case 级快评（通过/打回，保吞吐）和品级深检（逐字段核对，保深度）是两套数字，不要互相推导。

### 5.5 错误分类建议（E1-E5）

| 类型 | 描述 | 责任方 | 处理方向 |
|---|---|---|---|
| E1 | 类目映射错误 | 语义（T5） | 工具描述加边界规则、知识数据集补 few-shot |
| E2 | 误判高销 | 策略/数据 | 阈值调整 |
| E3 | 理由幻觉（数字与工具返回不符） | 生成（T6） | 理由模板化（占位符填充） |
| E4 | 格式违规 | 工程 | 校验重试 |
| E5 | 漏检（金标品未进清单） | 召回 | 策略迭代 |

归因的价值：责任方不同，处理路径完全不同——E3 占比低但伤害大优先修，E1 占比高是长期主线。

### 5.6 实施顺序（vibe coding 提示词序列）

按顺序投喂给 Claude Code / Cursor，每个做完验收再下一个：

```
PR1（Case 记录）：
  在 src/lib/agent/chat-runner.ts 的 runChatConversation 增加可选的
  onCaseRecord 回调，把每次完整选品运行（口径、工具调用序列、输出清单、
  自动评测四指标）持久化到 data/runtime/cases.json。

PR2（Case 池 + 评审工作台）：
  新增 /cases 页面：运行记录表格（竞对/品类/状态筛选）+ /review/[id] 评审页
  （三栏：自动评测指标 / 决策链路时间线 / 输出清单带真值比对高亮），
  底部通过/打回+E1-E5 标注，写入持久化。

PR3（Prompt 实验室）：
  新增 /prompts 页面：编辑 systemPrompt、六个工具描述、类目知识、T4 权重，
  保存为版本（data/prompts.json 增加自定义版本机制，内置版本只读）。

PR4（回归测试）：
  固定口径集（建议 30-50 个，覆盖 6 竞对 × 12 品类分层抽样）批量回放，
  并发执行，输出版本对比报告（四指标 + E1-E5 分布 + 涨跌）。

PR5（部署收尾）：
  部署到 Vercel，DEEPSEEK_API_KEY 配环境变量，准备 60 秒演示录屏。
```

**验收标准**：改 T5 工具描述 → 跑回归 → 类目对齐准确率可见变化，且分错误类型没有恶化——这个闭环跑通，平台就算成了。
